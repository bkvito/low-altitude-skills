# Skill 合集项目结构思路文档

## 目标判断

用户希望参考 `antfu/skills` 创建自己的 Skill 合集项目，但当前还不确定哪些目录和文件是必须的，哪些只是高级维护场景下才需要。因此本次整理的重点是区分“最小可用结构”和“完整自动化结构”。

## 思路说明

本次方案采用分层设计：

第一层是最小可用结构，只保留能够让 Skill 被识别、维护和阅读的核心文件。

第二层是推荐结构，为每个 Skill 增加 `references/`，让入口文件保持简洁，把详细规则拆到独立文档。

第三层是完整结构，在需要从外部仓库同步、生成或批量检查 Skill 时，再引入 `sources/`、`vendor/`、`instructions/`、`meta.ts` 和 `scripts/`。

## 关键判断

`skills/{skill-name}/SKILL.md` 是最核心文件，因为 Agent 读取 Skill 时需要一个明确入口。

`references/` 不是硬性要求，但对长期维护很重要，因为 Skill 通常会持续增长，入口文件过长会降低可读性。

`sources/` 和 `vendor/` 不适合一开始就加入，因为它们通常服务于自动同步或生成流程。如果当前只是维护自己的几个 Skill，提前引入这些目录会增加无效复杂度。

`package.json`、`meta.ts` 和 `scripts/` 也不是必要项。只有当项目开始需要自动化检查、同步、生成、安装或发布时，才需要这些配置。

## 方案取舍

本次建议优先选择手写维护版结构。原因是当前目标是建立 Skill 合集，而不是马上建设完整的同步系统。轻量结构更容易启动，也方便后续按真实需求扩展。

如果后续 Skill 数量增加，或者需要定期同步外部项目文档，再把自动化层补上即可。这样可以避免一开始就维护复杂脚本、子模块和元数据配置。

## 后续演进方向

后续可以按以下顺序演进：

1. 创建基础目录和几个 Skill。
2. 为每个 Skill 拆分 `references/`。
3. 增加 README，说明可用 Skill 列表。
4. 增加 AGENTS.md，定义仓库维护规则。
5. Skill 数量变多后再引入 `meta.ts` 和 `scripts/`。
6. 需要外部同步时再引入 `sources/`、`vendor/` 和 `instructions/`。
